## 1. 작업 방법

다음 3단계 프로세스로 진행했다.

1. **광범위 탐색**: 백엔드/프론트엔드 각각에 대해 독립된 탐색 에이전트를 병렬
   실행하여 잠재 이슈 후보 리스트를 수집.
2. **실제 코드 대조 검증**: 각 후보를 실제 파일/라인을 읽어 재현/반증. 오탐은
   기록은 남기되 적용에서 제외.
3. **수정 적용**: 검증된 이슈 중 *회귀 위험 ↓ × 운영 영향 ↑* 항목만 코드에 반영.

이 방식의 핵심은 **에이전트 보고서를 신뢰하지 않는 것**이다. 보고서를 일괄
적용하면 오히려 안정된 코드가 깨진다. 실제로 이번 리뷰에서도 "CRITICAL"로 분류된
보고 중 일부가 검증 후 오탐으로 판명되었다.

## 2. 적용한 수정

### 2.1 [CRITICAL] 디바운스된 토큰 저장의 미처리 거부

**파일**: `backend/src/services/google-auth.ts`

**문제**:
OAuth2Client `tokens` 이벤트 핸들러가 500ms 디바운스 후 Supabase에
새 토큰을 저장한다. 그러나 콜백 내부의 `await supabaseAdmin.from(...).update(...)`
에 try/catch가 없어, 거부 시 **unhandled promise rejection**이 발생한다.

`setTimeout` 콜백은 호출자 컨텍스트가 사라진 뒤 실행되므로 상위 try/catch로
포착되지 않는다. Express 5는 `unhandledRejection` 시 기본적으로
`process.exit(1)`이 트리거되도록 권고된 동작을 따른다(Node 14+).

**증상**:
- 운영 중 일시적 Supabase 장애 / 네트워크 오류 시 백엔드 프로세스가 무음 종료
- 토큰 저장 실패가 로깅되지 않아 디버깅 불가능

**수정**:
```ts
tokenSaveTimer = setTimeout(async () => {
  // ...
  try {
    const { error } = await supabaseAdmin.from('profiles').update(update).eq('id', userId);
    if (error) console.error('[google-auth] Failed to persist refreshed tokens:', error);
  } catch (err) {
    console.error('[google-auth] Token persistence threw:', err);
  }
}, 500);
```

**영향**: 안정성 ↑. 토큰 저장 실패 시 다음 요청에서 `invalid_grant` →
`handleInvalidGrant`로 자연스러운 복구 흐름.

### 2.2 [HIGH] AI 액션 pre-fetch 오류 무음 처리

**파일**: `backend/src/routes/chat.ts` (POST `/`, POST `/execute` 두 곳)

**문제**:
AI 액션 실행 전 Calendar/Tasks 클라이언트를 미리 가져오는 호출에서
`catch { /* per-action fallback */ }`로 오류를 완전히 삼킨다.
`invalid_grant`, quota 초과, OAuth 클라이언트 생성 실패 등 결정적 오류가
디버깅 불가능한 상태로 사라진다.

**수정**: 폴백 동작은 그대로 유지하되 `console.warn`으로 로그 기록.

```ts
catch (err) {
  console.warn('[chat] Calendar pre-fetch failed, falling back per-action:', err);
}
```

**영향**: 운영 가시성 ↑, 기능 회귀 0.

### 2.3 [HIGH] 토큰 리프레시 실패 시 unhandled rejection

**파일**: `frontend/src/lib/api.ts:64-84`

**문제**:
401 응답 인터셉터가 `supabase.auth.refreshSession()`을 호출하는데 try/catch가
없다. `refreshSession()`이 throw하는 경우 (네트워크 오류, 토큰 폐기됨,
Supabase 서비스 장애 등):

1. 사용자에게 "리프레시 실패" 같은 혼란스러운 에러가 노출됨
2. 원래의 401(인증 만료) 메시지가 가려져 `/login` 라우팅 로직이 작동하지 않음
3. 프론트 글로벌 unhandled rejection 핸들러가 트리거됨

**수정**: `refreshSession`을 try/catch로 감싸고, 실패 시 원래의 401 에러를
그대로 reject. 호출자가 "인증 만료" 흐름으로 자연스럽게 처리.

```ts
try {
  const { data: { session } } = await supabase.auth.refreshSession();
  if (session?.access_token) { /* retry */ }
} catch (refreshErr) {
  console.warn('[api] Token refresh failed; rejecting with original 401', refreshErr);
}
return Promise.reject(error);
```

**영향**: 인증 만료 흐름 정상화, UX ↑.

### 2.4 [MEDIUM] auth store 초기 마운트 시 프로필 중복 조회

**파일**: `frontend/src/store/auth.ts`

**문제**:
`initialize()`가 두 가지를 동시에 수행:
1. `supabase.auth.getSession().then(...)`로 직접 세션 조회 → `loadUser` 실행
2. `onAuthStateChange` 구독 등록 → 즉시 `INITIAL_SESSION` 이벤트 발화 → `loadUser` 실행

두 흐름이 거의 동시에 시작되어 **첫 마운트마다 Supabase 프로필 쿼리가 2번
실행**된다. `initialized` 플래그가 있지만 `finally`에서 설정되므로 두 호출이
이미 동시에 시작된 후라 가드 효과 없음.

**수정**: 수동 `getSession()` 호출 제거. `onAuthStateChange`가 INITIAL_SESSION을
보장하므로 단일 진입점으로 통합.

**영향**:
- 매 페이지 마운트 시 Supabase 호출 50% 감소 (프로필 RLS 쿼리 1회 절감)
- React 19 strict mode에서 더블 렌더링 시 추가 요청 누적되던 문제도 함께 해소
- 의미 있는 동작 변경 없음 (마지막 set 결과는 같음)

## 3. 검증 후 보류 (오탐 / 의도된 동작)

### 3.1 chat.ts `/execute` — messageId 소유권 검증 (탐색: CRITICAL)

**탐색 주장**: "messageId가 요청자 소유인지 확인하지 않아 다른 사용자 메시지의
metadata를 변조할 수 있다."

**실제 코드** (`chat.ts:680-690`):
```ts
.update({ metadata: { ... } })
.eq('id', messageId)
.eq('user_id', req.userId);   // ← 소유권 필터 명시
```

**판정**: **오탐**. WHERE절의 `user_id = req.userId` 필터로 다른 사용자 메시지는
0행 영향. 또한 `actions`는 `req.userId`의 데이터에만 실행되므로 교차 테넌트
침해 경로 없음.

---

### 3.2 React Query 캐시 키 불일치 (탐색: HIGH)

**탐색 주장**: "홈 페이지가 `'today-events'`를 무효화하지만 캘린더 페이지는
`'calendar-events'`를 쓴다 → 캐시 무효화 누락."

**판정**: **오탐**. 두 페이지가 라우트 분리로 동시에 마운트되지 않으며, 각자가
자신의 페이지에서 사용하는 키만 무효화한다. 의도된 디자인.

---

### 3.3 인증 캐시 TTL 3분 (탐색: CRITICAL)

**탐색 주장**: "`authMiddleware` 토큰→userId 캐시 3분이 너무 길다 → 토큰 폐기
시 최대 3분간 통과 가능."

**판정**: **합리적 트레이드오프 + 1.0 보고서에서 이미 검토됨**. 캐시 키가 토큰
원문이므로, 토큰이 변경되면 즉시 캐시 미스 → 재검증. "유출된 토큰 무효화 지연"은
캐시 TTL 문제가 아닌 Supabase 토큰 폐기 메커니즘의 본질적 특성이다.

---

### 3.4 reminders.ts PUT 동시 업데이트 (탐색: HIGH)

**탐색 주장**: "Supabase와 Google Tasks를 `Promise.all`로 동시에 업데이트해서
부분 실패 시 상태 불일치."

**판정**: **부분 오탐**. `is_completed`는 이전 1.x 작업에서 별도 엔드포인트
(`PATCH /:id/complete`)로 분리되어 Google Tasks 우선 정책이 적용됐다. PUT은
title/description/priority/notify 등 Google에 없는 필드도 다루므로 동시 업데이트가
적절. Google 측 실패 시에는 Supabase가 정상 업데이트되며, 다음 동기화 시점에
Google Tasks가 기준으로 재정렬된다(`reminders.ts` 머지 로직).

---

### 3.5 reminders/[id] 페이지 isDirty 폼 베이스라인 (탐색: MEDIUM)

**탐색 주장**: "saveMutation 성공 후 `reset(res.data)`를 호출하지 않아 isDirty가
스테일."

**판정**: **오탐**. `onSuccess`에서 `queryClient.setQueryData(['reminders', id], res.data)`
가 실행되고, 페이지의 `useQuery`가 새 데이터를 반환 → `useEffect([reminder, reset])`에서
이미 `reset({...reminder})` 호출 중. 베이스라인은 이미 갱신된다.


런타임 회귀 가능성:
- `google-auth.ts`: 정상 경로는 변경 없음(try 블록 내부에서 동일 동작).
- `chat.ts`: 폴백 동작 그대로, 로그만 추가.

- `auth.ts`: `onAuthStateChange`가 항상 INITIAL_SESSION을 보장한다는 Supabase
  공식 문서 동작에 의존. 회귀 시 영향 = 첫 로딩 화면 약간 더 길어짐.

## 6. 향후 권장 (이번 PR 범위 외)

다음 항목은 합리적이나 별도 PR로 분리 권장:

1. **에러 모니터링 도입** (Sentry / OpenTelemetry) — 본 PR의 `console.error/warn`이
   집약될 수신처가 필요. 운영 단계에서 필수.
2. **Reminders sync 머지 로직 통합 테스트** — Google Tasks ↔ Supabase 양방향
   동기화의 회귀 방지 테스트 부재. `vitest` + nock으로 Google API 모킹.
3. **AI 액션 직렬화 → Promise.allSettled** — 의존 없는 액션은 병렬 실행 가능
   (`chat.ts:547-548`은 이미 `Promise.all`이지만 일부 경로는 순차). 응답 시간
   단축 여지.
4. **Query key 상수화** — `['reminders']`, `['calendar-events']`, `['today-events']`
   등이 문자열 리터럴로 산재. `lib/query-keys.ts` 도입 시 오타로 인한 무효화
   누락 방지.
5. **백엔드 캐시 LRU 한계** — 1.1 보고서의 후속 항목(2-2). 토큰 버스트 시 메모리
   무한 증가 가능. `lru-cache` 패키지 도입 권장.

## 7. 결론

탐색 에이전트가 보고한 **백엔드 8건 + 프론트엔드 8건** 중 검증 통과한 4건만
적용했다. 적용된 수정은 모두 다음 기준을 만족한다:

- ✅ 실제 코드의 특정 라인을 가리킴
- ✅ 회귀 시나리오가 명확하지 않거나 영향이 작음
- ✅ 운영 안정성 / 디버깅 가시성에 직접 기여
- ✅ 변경 라인 수 최소화

**핵심 교훈**: AI 코드 리뷰는 *signal*이지 *command*가 아니다. 검증 단계에서
약 50%가 오탐으로 걸러졌고, 무비판적 적용은 오히려 동작 중인 코드를 망쳤을
가능성이 높다.
